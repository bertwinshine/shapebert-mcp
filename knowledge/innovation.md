# How to be innovative (read when the user asks for something new)

Read this whenever the request says innovative, unique, novel, creative, original,
different, bold, concept, or "surprise me". It exists because the easy mistake is to
hear "innovative boat" and quietly build a normal boat. That is the one thing the
user did NOT ask for. This file is the method for doing better. It does not replace
the engineering: once you pick a bold concept, you still run the domain file's
calculations and checks on it.

## The trap to avoid
Your default is to reach for the safest, most standard solution. For a normal request
that is correct. For an innovation request it is failure. A sensible, conventional
answer to "design something unique" is a wrong answer, even if it is well engineered.

## The method (do this in order, before building)
1. **Name the obvious answer, then set it aside.** Say in one line what the normal,
   expected design would be. That is your baseline to beat, not your plan.
2. **Generate at least three genuinely different directions.** Not three tweaks of the
   same shape. Three different ideas. Use the innovation moves below to get there.
3. **Show the user the options and let them pick.** List the 2 to 3 strongest with a
   one line trade-off each, then build the one they choose. Do NOT silently commit to
   one idea. Offering real choices is itself the fix for "it just made one normal boat".
4. **Pick bold but buildable.** The chosen idea must still meet the hard constraints
   (size, load, process, budget). Innovative and impossible is not innovative.
5. **Then engineer it.** Run the matched domain's calculations and checks. Report what
   is a concept and what is verified, exactly as for any other build.

## Innovation moves (how to actually get different ideas)
- **Combine two things that usually live apart.** A wave-piercing bow AND a tunnel
  hull. A seat that is ALSO a buoyancy tank. A rib that is ALSO a wire-tension channel.
  The novelty is in the pairing.
- **Turn a constraint into the feature.** The printing overhang limit becomes a bold
  faceted identity. The weak layer direction becomes a reason for visible tensioned
  tendons. Let the thing you were fighting shape the look.
- **Question the type itself.** Does it even need to be a monohull? A single piece?
  A boat at all? Ask what the user actually needs before assuming the usual form.
- **Integrate, remove parts.** The strongest concepts delete the separate frame, mould,
  foam or bracket by folding that job into the main shape. Fewer parts often reads as
  more advanced.
- **Give it one clear identity.** A bold, coherent silhouette that looks like nothing
  else is a feature, not decoration. A design people remember has done something right.
- **Change the scale or the number.** One big thing instead of many small. Many small
  instead of one big. A different count can be the whole idea.

## Reference examples
Run `search_examples` with words like innovative, concept or the product type. Past
designs in the knowledge base, including honest near misses, show what made an idea
work or fail. Learn the reason, don't copy the shape.

## Stay honest
Being bold is not an excuse to oversell. Say which parts are a concept, which are
checked, and what must be built and tested for real. A striking idea with an honest
status beats a safe idea dressed up as finished.
